# Sprint S12 — Backend e Autenticação

> **Estado:** Em andamento  
> **Registro:** contemporâneo  
> **Roadmap:** [Sprint 12](../roadmap.md#sprint-12--backend-e-autenticação)

## Objetivo

Integrar a autenticação com a API própria do MykytaDu (`mykytadu-api`) de forma segura,
desacoplada e multiplataforma nos 5 targets ativos (Android, Desktop, iOS, JS e WasmJS),
respeitando os contratos documentados (`openapi.yaml` e RFC 9457 Problem Details), garantindo
armazenamento seguro de tokens (`refreshToken` em storage protegido do SO e `accessToken`
estritamente volátil em memória), sessão restaurável e aplicação real de `RouteAccess`.

## Baseline

- As Sprints S1 a S11 entregaram fundação KMP/Compose, design system, catálogo AniList, persistência local da biblioteca e tela de configurações com preferências;
- A rota `AppRoute.Login` e a `LoginScreen` existem apenas como placeholder de navegação;
- A enum `RouteAccess` classifica rotas entre `PUBLIC` e `PROTECTED`, mas não havia sessão de autenticação ativa para impor bloqueios;
- A API própria possui contratos oficiais consolidados em `openapi.yaml`, `guia-cliente-kmp.md` e `catalogo-de-erros.md` (rotas `/api/v1/auth/login`, `/api/v1/auth/register`, `/api/v1/auth/refresh`, `/api/v1/auth/logout`);
- O aplicativo opera com 5 targets ativos (Android, Desktop, iOS Metadata, JS e WasmJS) com testes 100% verdes.

## Critérios de aceite

- [ ] O usuário pode cadastrar-se, entrar e sair com feedback visual claro de sucesso ou erro.
- [ ] A sessão é restaurada após reiniciar o aplicativo caso exista refresh token válido.
- [ ] `accessToken` permanece estritamente em memória volátil e tokens nunca são gravados em preferências comuns ou expostos em logs.
- [ ] O armazenamento seguro de `refreshToken` utiliza mecanismos protegidos específicos de cada plataforma.
- [ ] Respostas de erro da API seguem o padrão RFC 9457 Problem Details com mapeamento para erros amigáveis de domínio.
- [ ] Rotas protegidas verificam a sessão real e redirecionam ao login quando não autenticado.
- [ ] Falhas de autenticação não apagam indevidamente dados da biblioteca local.
- [ ] Todos os targets ativos (Android, Desktop, iOS Metadata, JS e WasmJS) mantêm compilação e testes verdes.

## Decisões arquiteturais

- O domínio de autenticação permanece isolado de detalhes de transporte HTTP, JSON e formatos de API;
- DTOs remotos utilizam Kotlinx Serialization e são restritos à camada de dados;
- Erros de autenticação retornados pela API no formato RFC 9457 (`application/problem+json`) são mapeados para `AuthFailure` no domínio com base no código estável (`code`), nunca pela mensagem livre (`detail`);
- `accessToken` tem ciclo de vida curto (10 min) e é mantido apenas em memória (`StateFlow` / Repository);
- `refreshToken` é persistido de forma segura via `SecureStorageDriver` específico por target;
- Para clientes Web, o navegador envia cookies `HttpOnly` e o cliente KMP Web não armazena tokens sensíveis em `localStorage`.
